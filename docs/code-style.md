# 代码注释与日志约定

这份约定用于 CareerAI 与 CareerHub 的业务代码。注释帮助读代码的人理解**为什么这样做**；方法名和清晰的代码本身负责说明**做了什么**。

## 注释写在哪里

- 复杂服务的类注释说明职责和与其他服务的边界。例如 Agent 只让模型提出动作，Java 决定能否读取岗位。
- 方法注释说明容易误解的前提、失败结果或事务范围。例如导入任务必须先保存文件与任务记录，再发送任务 ID。
- 行内注释放在不明显的决策旁边。例如“超时也占用一步”“模型只能读取搜索得到的岗位 ID”。
- 不给简单赋值、普通 `if` 和每一步顺序机械编号。代码变化后，过多的逐行注释容易和实现不一致。

## 日志怎么写

- 使用 SLF4J 占位符：`log.warn("event=agent.resume_read_failed traceId={} httpStatus={}", traceId, status);`。`{}` 会按参数顺序填入值；`log.warn` 本身是规范的警告级日志调用。
- `event` 使用稳定的业务名，不使用 `U48`、`U52` 等学习进度编号。这样后续重构学习计划时，线上日志的含义仍清晰。
- 同一请求用 `traceId` 串联开始、动作、失败与结束；失败记录阶段、HTTP 状态或异常类型。预期的业务拒绝不要一律当作系统崩溃。
- 不记录 Bearer Token、密码、简历正文、完整 JD、Prompt 或未经处理的搜索词。下游异常消息可能含请求数据，写日志前先判断是否安全。
- `info` 表示正常进度，`warn` 表示可恢复或已转成部分结果的异常，`error` 表示非预期的服务故障。日志不代替返回给用户的清晰错误信息。

## 这轮改动的业务边界

- CareerHub 的 JWT 拦截器负责建立并清理请求线程里的用户身份。
- CareerAI 的工具实例绑定选定简历和登录凭证；Prompt 只引导模型，真正的权限和次数限制由 Java 执行。
- Agent 的 `stepsUsed` 在模型调用前计数，超时也占一步；完整 JD 必须来自搜索到的候选岗位。
- RabbitMQ 消息只携带任务 ID；文件和进度由持久化存储保存，消费端通过任务状态处理重复消息。
- RAG 重建先完成向量计算，再用 PostgreSQL 事务替换旧索引，避免 Embedding 失败时删除旧块。
